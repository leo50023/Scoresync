# Audience Voting (People's Choice Award) for ScoreSync

This change adds a complete QR-code-based audience voting system layered on top of the existing judge-scoring flow. A new `votes` Firestore subcollection under each event records one vote per device fingerprint. The voting page (`/events/:eventId/vote`) is public, shows a live contestant grid with vote bars, and auto-refreshes counts every 10 seconds via a JSON polling endpoint. Admins and organizers can open/close voting from the event show page, and the results page gains a People's Choice section showing the audience ranking. Watch for: the fingerprint-based duplicate-vote check is a soft barrier that a moderately determined voter can bypass, and there are no admin-visible voter records beyond the raw Firestore subcollection.

**Verdict**: APPROVED

---

## High-level view

The controller is complete and matches the spec precisely: all 5 handlers are present, fingerprinting uses `crypto.createHash('sha256')` over IP+User-Agent, the Firestore duplicate check queries by fingerprint before writing, `voteCounts` returns JSON with `Cache-Control: no-store`, and `toggleVoting` flips `event.votingOpen`. The only behavioural gap is that the fingerprint barrier is bypassable with a different IP or a changed User-Agent string — this is an architectural limitation of the approach, not an implementation bug, but it should be understood by operators.

Routes are registered in the correct order and before the `/display` public route, which is important because Express route matching is positional. Auth guards are exactly as specced: GET `/vote` and POST `/vote` are unauthenticated (intentional — audience members don't have accounts), GET `/vote/results` requires auth, POST `/vote/toggle` requires auth + role guard.

The voting page omits the sidebar (correct for a public-facing page), has flash banners, hero with event name and open/closed badge, a contestant grid with per-contestant vote forms, vote buttons disabled server-side when `votingOpen` is false, and the localStorage deduplication plus 10-second live-refresh client script. The QR overlay loads the library lazily from CDN.

The `show.xian` changes are fully present in both the admin dropdown (`admin-more-content`) and the organizer dropdown (`org-more-content`): "Audience Voting" link and "Open Voting"/"Close Voting" toggle form in both. The hero voting badge is present immediately after the status badge.

`scoringController.resultsPage` extends the `Promise.all` to 5 items, builds `votesByContestant` and `totalAudienceVotes`, then attaches `audienceVoteCount` and `audienceVotePct` to each ranked contestant after tie-breaking and rank assignment. Both `votesByContestant` and `totalAudienceVotes` are passed to the render call.

`results.xian` includes the People's Choice section gated on `{{#if totalAudienceVotes}}`, iterates `ranked`, uses `{{lookup ../votesByContestant id}}` for the vote count display, and uses `audienceVotePct` for the bar width. The `lookup` helper is registered in `index.js`.

<details>
<summary>Issues (2)</summary>

1. **Fingerprint bypass** — IP + User-Agent fingerprinting is a soft barrier. A voter behind a VPN or phone data connection can vote again after switching networks, and the User-Agent is trivially changed. Operators should be informed this is rate-limiting, not hard deduplication. No code change required if this is an accepted trade-off, but the UI should communicate it.

2. **`voteResults` handler is a redirect stub** — the route `GET /events/:eventId/vote/results` exists and redirects to the voting page, which is intentional (results are shown inline). However it is protected by `requireAuth`, meaning a logged-in user hitting it gets a redirect loop back to the voting page that is itself public. This is harmless but the route could be removed to avoid confusion, or its auth requirement dropped to match the voting page.

### Fingerprint duplicate-vote enforcement

The duplicate check at `submitVote` queries `events/{eventId}/votes` for any document where `fingerprint == fp` before writing. This is confirmed to be a Firestore `where` query and not an in-memory check, so it will work correctly even under concurrent submissions. The fingerprint is `sha256(ip | user-agent)`, which matches the spec exactly.

The soft-barrier nature is confirmed: `req.ip` on Vercel will reflect the forwarded IP from the edge proxy (the `x-forwarded-for` header), and two separate devices or VPN exits will produce different fingerprints and both succeed. This is the intended approach per the plan and is acceptable for a community voting context; it is noted here for operator awareness.

### `voteResults` redirect and its auth guard

`voteResults` redirects to `/events/${eventId}/vote`. The `/vote` route requires no auth. So a logged-in user navigating to `/vote/results` gets a 302 to `/vote`, which renders correctly. An unauthenticated user cannot reach `/vote/results` due to `requireAuth`, but they don't need to because the voting page is the canonical URL. The route is functional but slightly inconsistent: the only reason to require auth on a redirect stub is if the route is expected to eventually serve its own view. If it stays a stub, dropping `requireAuth` or removing the route entirely would clean this up.

### `lookup` helper registration

Confirmed present in `index.js`:
```js
hbs.registerHelper("lookup", (obj, key) => (obj && obj[key] !== undefined) ? obj[key] : 0);
```
This is registered before the `.xian` engine is set up, so it is available to all templates including `results.xian`.

### No test coverage

No test files were added for the voting controller or routes. The spec did not call for tests in this iteration, and the project does not appear to have an existing test framework configured. Not flagged as a blocker but worth noting for future hardening.
